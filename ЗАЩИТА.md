## 1. JavaScript-фреймворки: React, Vue, Angular, Svelte. Основные особенности и различия

Все четыре решают одну задачу: описывать интерфейс **декларативно** (UI = f(state)) из **компонентов**,
а обновление DOM при изменении данных берут на себя. Различаются тем, *как* они отслеживают изменения
и *сколько* всего дают «из коробки».

| | React | Vue | Angular | Svelte |
|---|---|---|---|---|
| Что это | библиотека для UI (Meta) | прогрессивный фреймворк | полноценная платформа (Google) | компилятор |
| Шаблоны | JSX (разметка внутри JS) | HTML-шаблоны с директивами (`v-if`, `v-for`) или JSX | HTML-шаблоны с control flow (`@if`, `@for`), биндинги `[prop]`, `(event)` | HTML-подобный синтаксис `{#if}`, `{#each}` |
| Язык | JS/TS | JS/TS | TypeScript (обязательно де-факто) | JS/TS |
| Реактивность | нет автоматической: `setState`/`useState` → повторный вызов функции-компонента | Proxy-реактивность (`ref`, `reactive`), автоматическое отслеживание зависимостей | раньше Zone.js + change detection, сейчас **Signals** (zoneless) | компилятор превращает присваивания в точечные обновления; в Svelte 5 — runes (`$state`, `$derived`) |
| Обновление DOM | Virtual DOM + reconciliation | Virtual DOM + компилятор помечает статические части | инкрементальный DOM (Ivy): шаблон компилируется в инструкции, обновляются только привязки | без Virtual DOM: компилятор генерирует прямые операции с DOM |
| Что «в коробке» | только UI. Роутер, состояние, формы, HTTP — сторонние (React Router, Redux/Zustand, TanStack Query) | ядро + официальные Vue Router и Pinia | всё: роутер, HttpClient, формы, DI, тесты, CLI, i18n, RxJS | ядро + SvelteKit (роутинг, SSR) |
| Глобальное состояние | Context, Redux Toolkit, Zustand | Pinia | сервисы + Signals, NgRx | stores / runes |
| Порог входа | средний | низкий | высокий (DI, RxJS, TypeScript, декораторы) | низкий |
| Размер бандла | средний | небольшой | самый большой | самый маленький |

Особенности Angular, которые используются в работе:
- **Dependency Injection** — сервисы (`AuthService`, `StudentsApi`) создаются фреймворком и внедряются
  через `inject()`; `providedIn: 'root'` делает их синглтонами.
- **Standalone-компоненты** без NgModule: каждый компонент сам перечисляет, что использует (`imports: [...]`).
- **RxJS встроен**: `HttpClient`, `Router`, Reactive Forms отдают `Observable`.
- **Signals** — новая модель реактивности, приложение работает без Zone.js (zoneless).
- **Строгая структура** — CLI, единый стиль, удобно для больших команд.

Когда что выбирают: React — огромная экосистема и свобода выбора; Vue — быстрый старт и простота;
Angular — крупные корпоративные приложения, где важны единые правила и всё из коробки;
Svelte — минимальный размер и производительность.

## 2. SPA и клиентская маршрутизация. Принципы работы одностраничных приложений

**SPA (Single Page Application)** — приложение, где браузер загружает **один** HTML-документ
(`index.html`) и JS-бандл, а дальше все переходы и обновления происходят без перезагрузки страницы:
JS сам перерисовывает нужную часть DOM, а данные получает через AJAX (fetch/XHR) в формате JSON.

Сравнение с **MPA** (Multi Page Application, как в лаб. 2 на Django): там каждый переход — новый
HTTP-запрос за полной HTML-страницей, сервер её рендерит, браузер всё перерисовывает с нуля.

| | MPA | SPA |
|---|---|---|
| Первая загрузка | быстрая | дольше (нужно скачать бандл) |
| Переходы | полная перезагрузка | мгновенно, без перезагрузки |
| Сервер отдаёт | HTML | статику один раз + JSON через API |
| Состояние | теряется между страницами | живёт в памяти JS |
| SEO | хорошо | хуже без SSR |

**Клиентская маршрутизация** — сопоставление URL с компонентом на стороне браузера.
Используется **History API**: `history.pushState()` меняет адрес в строке без запроса к серверу,
а событие `popstate` срабатывает на кнопки «назад/вперёд». Роутер слушает изменения URL и
показывает в `<router-outlet>` нужный компонент. (Старый вариант — hash-маршрутизация `/#/students`,
она не требует настройки сервера.)

В проекте:
- `app.routes.ts` — таблица `путь → компонент`, `title` и `canActivate` (guards).
- `routerLink="/students"` вместо обычной ссылки: клик перехватывается, страница не перезагружается.
- `:id` — параметр маршрута, `withComponentInputBinding()` передаёт его в `input()` компонента.
- Query-параметры (`/students?search=анна&sort=-id&page=2`) хранят состояние списка — его можно
  обновить, сохранить в закладки, пройти «назад».
- `**` — страница 404 для неизвестных путей.

**Проблема прямого захода по ссылке.** Если открыть `http://site/students/5` напрямую, браузер
сделает запрос к серверу, а такого файла нет. Поэтому веб-сервер должен на любой неизвестный путь
отдавать `index.html` — в Nginx это `try_files $uri $uri/ /index.html;`. Дальше Angular сам
разберёт URL и покажет нужную страницу.

## 3. Компонентная архитектура. Компоненты, props, события и взаимодействие между компонентами

**Компонент** — независимый переиспользуемый блок интерфейса: шаблон (HTML) + стили (CSS, изолированные
для компонента) + класс с логикой (TS). Приложение — дерево компонентов: `App` → `Navbar`, `Notice`,
`router-outlet` → страница `Students` → `FilterPanel`, `Pagination`, `Loader`.

**Props (в Angular — inputs)** — входные данные от родителя. Идут **только сверху вниз**,
дочерний компонент их не меняет, они описывают внешний «контракт» компонента:

```ts
export class Pagination {
  readonly page = input.required<number>();
  readonly totalPages = input.required<number>();
  readonly disabled = input(false);
  readonly pageChange = output<number>();
}
```
```html
<app-pagination [page]="page.page" [totalPages]="page.totalPages" (pageChange)="changePage($event)" />
```

**События (outputs)** — способ ребёнка сообщить родителю о действии: снизу вверх.
Аналог в React — callback-props (`onChange={...}`), во Vue — `emit`.
`Pagination` не знает, что делать при смене страницы, — она лишь вызывает `pageChange.emit(n)`,
а родитель `Students` меняет URL. Так компонент остаётся переиспользуемым.

Способы взаимодействия компонентов:
1. **Родитель → ребёнок**: inputs (`[student]="..."`).
2. **Ребёнок → родитель**: outputs (`(submitted)="save($event)"`).
3. **Между далёкими компонентами**: общий сервис/хранилище (`AuthStore`, `NoticeStore`): `Navbar` и
   `Profile` читают один и тот же сигнал `user`. Это решает проблему **props drilling** — когда данные
   приходится передавать через много промежуточных компонентов, которым они не нужны.
4. **Через маршрут**: параметры URL (`:id`, query-параметры).
5. Двустороннее связывание `[(value)]` = input + output `valueChange` (`model()` в Angular).

Деление на **«умные» и «глупые»** компоненты:
- *Страницы* (container/smart) — знают про сервисы, роутер, загружают данные: `Students`, `StudentEdit`.
- *Презентационные* (dumb) — только inputs/outputs: `StudentCard`, `Pagination`, `StudentForm`, `UserCard`.
  Например, `StudentForm` используется и для создания, и для редактирования: разница только в том,
  передан ли `[student]`.

## 4. Жизненный цикл компонентов. Hooks и lifecycle-механизмы

Компонент **создаётся → получает входные данные → отображается → обновляется → уничтожается**.
Фреймворк даёт «крючки», чтобы выполнить код в нужный момент.

**Angular** (в порядке вызова):

| Хук | Когда | Зачем |
|---|---|---|
| `constructor` | создание класса | `inject()` зависимостей, подписки с `takeUntilDestroyed()` |
| `ngOnChanges(changes)` | при каждом изменении inputs (и до `ngOnInit`) | реагировать на новые входные данные |
| `ngOnInit` | один раз после первого `ngOnChanges` | начальная загрузка данных |
| `ngDoCheck` | каждый цикл проверки | своя логика обнаружения изменений (редко) |
| `ngAfterContentInit / Checked` | после проецирования `<ng-content>` | |
| `ngAfterViewInit / Checked` | после отрисовки своего шаблона и детей | работа с DOM, `@ViewChild` |
| `afterNextRender / afterEveryRender` | после рендера (новое API) | замеры DOM, сторонние библиотеки |
| `ngOnDestroy` / `DestroyRef.onDestroy` | перед удалением | отписки, таймеры, освобождение ресурсов |

В проекте:
- `StudentForm.ngOnChanges(changes)` — когда родитель передал студента, форма заполняется его данными,
  поле ИСУ блокируется. Проверка `changes['student']` нужна, чтобы изменение `busy` не сбросило
  введённые значения.
- `UserCard.ngOnChanges` — после сохранения список перезагружается, приходит новый объект `user`,
  и карточка выходит из режима редактирования.
- `takeUntilDestroyed(destroyRef)` — подписка автоматически завершится в момент уничтожения компонента.
- `effect()` и `computed()` из Signals тоже живут столько же, сколько компонент.

**React (hooks)** — функциональные компоненты, жизненный цикл выражается хуками:
- `useState` — локальное состояние; `useEffect(fn, deps)` — побочный эффект после рендера,
  `deps = []` ≈ «при монтировании», возвращаемая функция — очистка ≈ «при размонтировании»;
  `useMemo`, `useCallback`, `useRef`, `useContext`. Правила: хуки вызываются только на верхнем
  уровне компонента и всегда в одном порядке.

**Vue**: `setup`, `onMounted`, `onUpdated`, `onUnmounted`, `watch`. **Svelte**: `onMount`, `onDestroy`,
в Svelte 5 — `$effect`.

## 5. Рендеринг интерфейса. Virtual DOM, reconciliation и условный рендеринг

Операции с реальным DOM дорогие (пересчёт стилей, layout, перерисовка), поэтому фреймворки
стараются менять DOM минимально.

**Virtual DOM** (React, Vue) — лёгкое JS-дерево объектов, описывающее, каким должен быть интерфейс.
При изменении состояния компонент заново строит новое виртуальное дерево.

**Reconciliation (согласование, diffing)** — сравнение нового виртуального дерева со старым и
вычисление минимального набора изменений, которые затем применяются к реальному DOM (commit).
Эвристики React, дающие O(n) вместо O(n³):
- элементы разного типа → поддерево пересоздаётся целиком;
- одинакового типа → обновляются только изменившиеся атрибуты;
- в списках элементы сопоставляются по **ключу** `key`. Без ключа при вставке в начало списка
  перерисуются все элементы, а состояние полей ввода «уедет» к соседям.

**Angular** не использует Virtual DOM. Компилятор Ivy превращает шаблон в набор инструкций
(*incremental DOM*): при проверке сравниваются только значения привязок (`{{ }}`, `[prop]`), и
меняются ровно те узлы, где значение изменилось. Аналог `key` — `track` в `@for`:
```html
@for (student of page.items; track student.id) { <tr>...</tr> } @empty { <tr>Студенты не найдены</tr> }
```
**Svelte** вообще без Virtual DOM: на этапе компиляции генерирует код вида «при изменении `x` обнови
этот текстовый узел».

**Условный рендеринг** — элемент добавляется в DOM или удаляется в зависимости от условия
(в отличие от CSS `display:none`, который лишь прячет элемент):
- Angular: `@if (cond) {...} @else if {...} @else {...}`, `@switch`, `@for ... @empty`, `@defer`;
- React: `cond && <X/>`, тернарный оператор; Vue: `v-if` / `v-show`.

В проекте: в навбаре `@if (store.isAdmin())` показывает ссылку «Пользователи»; на странице списка —
`@if (state().error)`, `@if (state().data)`, `@if (state().loading)`; кнопки изменения видны только
администратору. В лаб. 3 то же делалось вручную классами `hidden`, `admin-only` и
`classList.toggle(...)`.

## 6. Реактивность во frontend. Механизмы отслеживания изменений и обновления интерфейса

**Реактивность** — интерфейс автоматически обновляется при изменении данных, программист описывает
только «что показать», а не «когда и как перерисовать».

Механизмы отслеживания изменений:
1. **Явное уведомление** (React): `setState(newValue)` говорит фреймворку «состояние поменялось» →
   компонент перерендеривается, затем reconciliation. Мутация объекта без `setState` не заметна.
2. **Dirty checking + Zone.js** (классический Angular): Zone.js патчит все асинхронные API
   (`setTimeout`, события, XHR, Promise). После любого из них Angular обходит дерево компонентов и
   сравнивает текущие значения привязок с прошлыми. Просто, но проверяет лишнее.
   Оптимизация — `ChangeDetectionStrategy.OnPush`.
3. **Proxy/геттеры** (Vue 3, MobX): объект оборачивается в `Proxy`; при чтении свойства
   запоминается, кто от него зависит (track), при записи — уведомляются зависимые (trigger).
4. **Signals** (Angular 16+, Solid, Preact, Vue `ref`, Svelte 5 runes) — «мелкозернистая» реактивность.
   Сигнал — контейнер значения, который знает своих потребителей:
   ```ts
   readonly user = signal<User | null>(null);              // записываемый
   readonly isAdmin = computed(() => this.user()?.role === 'ADMIN'); // производный, ленивый, кэшируется
   effect(() => console.log(this.user()));                 // побочный эффект
   ```
   При чтении `user()` внутри шаблона/`computed` создаётся связь; `user.set(...)` помечает
   зависимых «грязными», и Angular перерисовывает **только** компоненты, читающие этот сигнал.
   Проект работает в **zoneless**-режиме (Zone.js не подключён) — изменения отслеживаются через
   сигналы, события шаблона и `async`/`toSignal`.
5. **Компиляция** (Svelte): компилятор видит присваивания и вставляет код обновления.
6. **Потоки (RxJS)** — push-модель: данные «текут» к подписчикам. Мост в сигналы — `toSignal()`,
   обратно — `toObservable()`. В проекте: `state = toSignal(query$.pipe(loadWith(...)))`.

Цикл обновления: изменение данных → уведомление/обнаружение → вычисление, что изменилось →
пакетное обновление DOM (batching: несколько изменений за один тик дают одну перерисовку).

## 7. Управление состоянием. Локальное и глобальное состояние, инструменты state management

**Состояние** — данные, от которых зависит интерфейс.

**Локальное** — нужно одному компоненту, живёт и умирает вместе с ним:
`showFilters`, `showExtra`, `confirmId` в `Students`; `editing` в `UserCard`; значения полей форм.
Правило: хранить состояние как можно ниже по дереву.

**Глобальное** — нужно многим компонентам в разных частях дерева: текущий пользователь, токены,
уведомления, корзина, тема. Передавать его props'ами через все уровни неудобно (props drilling),
поэтому его выносят в **хранилище (store)** — единый источник истины.

Ещё виды: **серверное** состояние (кэш данных с API — TanStack Query, `loadWith` в проекте),
**состояние URL** (фильтры, страница — в query-параметрах), **состояние форм**.

Инструменты:
- React: Context API (для редко меняющихся данных), Redux Toolkit (единый store, actions, reducers,
  неизменяемость, DevTools), Zustand (минималистичный store на хуках), MobX.
- Vue: Pinia (state, getters, actions).
- Angular: сервисы-синглтоны + **Signals**; **NgRx** (Redux-подход на RxJS: Store, Actions, Reducers,
  Effects, Selectors), NgRx SignalStore.
- Svelte: stores (`writable`, `derived`), runes.

**Redux-подход** (однонаправленный поток данных): View → `dispatch(action)` → `reducer(state, action)`
возвращает **новое** состояние → View перерисовывается. Состояние меняется только явными действиями,
поэтому изменения предсказуемы и их легко отлаживать.

В проекте — `AuthStore` на Signals:
```ts
@Injectable({ providedIn: 'root' })
export class AuthStore {
  readonly user = signal<User | null>(null);
  readonly accessToken = signal<string | null>(localStorage.getItem(ACCESS_KEY));
  readonly isLoggedIn = computed(() => this.user() !== null);
  readonly isAdmin = computed(() => this.user()?.role === 'ADMIN');
  setTokens(tokens) {...}  setUser(user) {...}  clear() {...}
}
```
Сигналы публичные для чтения, а меняются через методы стора — так все изменения проходят в одном месте.
Им пользуются `Navbar`, guards, interceptor, `Profile`, `Students`. `NoticeStore` — глобальная очередь
уведомлений. Токены дополнительно сохраняются в `localStorage`, чтобы сессия пережила перезагрузку
страницы, а при старте `provideAppInitializer` восстанавливает пользователя через `/api/auth/me`.

## 8. Реактивное программирование. Основные принципы и отличия от императивного подхода

**Реактивное программирование** — парадигма, в которой программа описывается как реакция на
**потоки данных/событий** во времени. Всё — поток: клики, ввод, HTTP-ответы, таймеры, URL.
Мы декларативно описываем, *как* потоки преобразуются и комбинируются, а изменения распространяются
автоматически.

Принципы:
- **потоки** — последовательность значений во времени (плюс ошибка и завершение);
- **декларативность** — цепочка операторов описывает «что получить», а не «как по шагам»;
- **композиция** — сложное поведение собирается из маленьких операторов;
- **push-модель** — источник сам отправляет данные подписчикам;
- **распространение изменений** — при новом значении на входе пересчитывается всё, что от него зависит;
- **ленивость** — ничего не происходит, пока нет подписки.

Пример — живой поиск. **Императивно** (как в лаб. 3):
```js
let timer, lastText, controller;
input.addEventListener('input', () => {
  clearTimeout(timer);
  timer = setTimeout(async () => {
    const text = input.value.trim();
    if (text === lastText) return;
    lastText = text;
    controller?.abort();                 // отменить старый запрос
    controller = new AbortController();
    try { render(await fetch(url + text, { signal: controller.signal })); } catch (e) { ... }
  }, 400);
});
```
Состояние размазано по переменным, легко ошибиться. **Реактивно**:
```ts
searchControl.valueChanges.pipe(
  map(text => text.trim()),
  debounceTime(400),
  distinctUntilChanged(),
  switchMap(text => api.list(text)),   // отменяет предыдущий запрос
).subscribe(render);
```

| Императивный | Реактивный |
|---|---|
| «как»: пошаговые команды | «что»: описание зависимостей |
| состояние в изменяемых переменных | состояние выводится из потоков |
| вызов функции при событии вручную | подписка на поток |
| сложно комбинировать асинхронность | операторы для времени, отмены, комбинирования |
| pull: мы запрашиваем значение | push: значение приходит само |

Недостатки: порог входа, сложнее отлаживать длинные цепочки, нужно помнить об отписке.

## 9. RxJS. Observable, Observer, Subject, BehaviorSubject и Subscription

**RxJS** — библиотека реактивного программирования для JS, реализует паттерн «Наблюдатель» +
«Итератор» и набор операторов.

**Observable** — ленивый поток значений. Ничего не делает, пока на него не подписались.
Может выдать 0..∞ значений (`next`), затем либо ошибку (`error`), либо завершение (`complete`) —
после них значений больше не будет.
```ts
const numbers$ = new Observable<number>(subscriber => {
  subscriber.next(1); subscriber.next(2); subscriber.complete();
  return () => { /* очистка при отписке */ };
});
```
Отличия от Promise: Promise — одно значение, «жадный» (запускается сразу), не отменяется;
Observable — много значений, ленивый, отменяемый, с операторами.

**Observer** — объект-получатель с тремя колбэками:
```ts
{ next: value => ..., error: err => ..., complete: () => ... }
```

**Subscription** — результат `subscribe()`, «билет» подписки. `subscription.unsubscribe()` останавливает
поток и вызывает функцию очистки (например, отменяет HTTP-запрос). Подписки можно объединять
`sub.add(other)`.

**Subject** — одновременно Observable и Observer: в него можно вручную «толкать» значения
(`subject.next(v)`), и он раздаёт их **всем** текущим подписчикам (multicast, hot). Поздний подписчик
прошлых значений не получает. В проекте: `Action` хранит `trigger = new Subject<T>()`, `run(value)`
вызывает `trigger.next(value)`.

**BehaviorSubject** — Subject с **текущим значением**: требует начальное значение, новому подписчику
сразу отдаёт последнее, есть `.value`. Подходит для состояния. В проекте:
`reload$ = new BehaviorSubject<void>(undefined)` — сразу запускает первую загрузку, а `reload$.next()`
перезагружает список после удаления.

Другие: **ReplaySubject(n)** — отдаёт новым подписчикам n последних значений;
**AsyncSubject** — только последнее значение при завершении.

## 10. Операторы RxJS. Преобразование, фильтрация, комбинирование и обработка потоков данных

Оператор — чистая функция `Observable → Observable`, подключается через `pipe(...)`.
Есть *создающие* операторы: `of`, `from`, `fromEvent`, `interval`, `timer`, `throwError`, `EMPTY`.

**Преобразование**
- `map(fn)` — преобразовать каждое значение: `map(tokens => tokens.accessToken)`.
- `scan(fn, seed)` — накопление (как `reduce`, но выдаёт промежуточные): в `loadWith` сохраняет
  прошлые данные на время новой загрузки.
- `switchMap` — для каждого значения запускает внутренний поток, **отменяя предыдущий** (поиск, загрузка по id).
- `mergeMap` — запускает все параллельно (независимые запросы).
- `concatMap` — по очереди, в порядке поступления (сохранение по порядку).
- `exhaustMap` — **игнорирует** новые значения, пока текущий поток не завершён (защита от двойной отправки
  формы — класс `Action`).
- `tap` — побочный эффект без изменения значения: `tap(tokens => store.setTokens(tokens))`.

**Фильтрация**
- `filter(pred)`, `take(n)`, `first()`, `skip(n)`, `takeUntil(notifier$)`, `takeUntilDestroyed()`;
- `debounceTime(ms)` — пропустить значение, только если после него была пауза ms (ввод в поиск);
- `throttleTime(ms)` — не чаще раза в ms (скролл, ресайз);
- `distinctUntilChanged(cmp?)` — отбросить значение, равное предыдущему (`sameQuery` для запроса списка).

**Комбинирование**
- `combineLatest([a$, b$])` — при любом изменении выдаёт последние значения всех: в `Students`
  объединяет параметры запроса и сигнал перезагрузки;
- `merge(a$, b$)` — сливает потоки в один; `concat` — последовательно;
- `forkJoin([a$, b$])` — ждёт завершения всех и выдаёт последние значения (параллельные запросы);
- `withLatestFrom(b$)` — при значении основного потока берёт последнее из другого;
- `zip` — попарно; `startWith(v)` — начать с значения; `race` — кто первый.

**Обработка ошибок и завершения**
- `catchError(err => of(fallback))` — перехватить ошибку и заменить потоком (иначе поток умирает);
- `retry({ count, delay })` — повторить при ошибке; `throwError(() => err)` — пробросить дальше;
- `finalize(fn)` — выполнить при завершении, ошибке или отписке (сброс `busy`, `refreshing$ = null`).

**Мультикаст**: `share()`, `shareReplay(1)` — один источник на всех подписчиков (одно обновление токена
на несколько упавших запросов).

Пример из проекта — оператор загрузки:
```ts
export function loadWith<Q, T>(request: (query: Q) => Observable<T>): OperatorFunction<Q, LoadState<T>> {
  return source => source.pipe(
    switchMap(query => request(query).pipe(
      map(data => ({ loading: false, data, error: null })),
      catchError(error => of({ loading: false, data: null, error: toAppError(error) })),
      startWith({ loading: true, data: null, error: null }),
    )),
    scan((previous, next) => (next.loading ? { ...next, data: previous.data } : next), start),
  );
}
```

## 11. Асинхронные потоки. Hot и cold Observable, управление подписками и предотвращение утечек памяти

**Cold (холодный)** Observable — источник данных создаётся **внутри** при каждой подписке; каждый
подписчик получает свою независимую последовательность с начала. Пример: `http.get()` — две подписки
дают **два** HTTP-запроса; `of()`, `interval()`.

**Hot (горячий)** — источник существует независимо от подписчиков и общий для всех; подписавшийся
позже пропускает прошлые значения. Примеры: `fromEvent(button, 'click')`, `Subject`, события роутера,
WebSocket.

Превратить холодный в горячий — **мультикаст**: `share()` (общий источник, пока есть подписчики),
`shareReplay({ bufferSize: 1, refCount: true })` (плюс помнит последнее значение для новых).
В проекте `refresh()` использует `shareReplay(1)`: если три запроса одновременно получили 401, будет
**один** запрос `/api/auth/refresh`, и все три дождутся нового токена.

**Утечки памяти.** Подписка держит ссылки на колбэки, а через них — на компонент. Если компонент
удалён, а бесконечный поток (`interval`, `valueChanges`, Subject, события роутера) продолжает
работать, компонент не будет собран сборщиком мусора, а колбэк выполнится на «мёртвом» компоненте
(лишние запросы, ошибки).

Как предотвратить:
- `takeUntilDestroyed(destroyRef)` — завершает поток при уничтожении компонента (используется во
  всех подписках проекта);
- `async` pipe и `toSignal()` — подписываются и отписываются автоматически вместе с компонентом;
- `takeUntil(destroy$)` + `destroy$.next()` в `ngOnDestroy` (классический вариант);
- хранить `Subscription` и вызывать `unsubscribe()` в `ngOnDestroy`;
- `take(1)` / `first()` для одноразовых значений;
- конечные потоки (HTTP-запрос завершается сам) отписки обычно не требуют, но отписка отменяет запрос.

## 12. Реактивная обработка пользовательских событий. Поиск, фильтрация и отмена устаревших запросов

Задачи при живом поиске:
1. не отправлять запрос на каждую букву — **debounce**;
2. не отправлять одинаковые запросы — **distinctUntilChanged**;
3. игнорировать пробелы по краям — **map(trim)**;
4. показывать результат только последнего запроса — **switchMap**. Без него возможна гонка
   (race condition): запрос «ан» ответил позже, чем «анна», и на экране устаревший результат.
   `switchMap` при новом значении отписывается от старого внутреннего Observable, а `HttpClient`
   при отписке вызывает `xhr.abort()` — запрос реально отменяется (в DevTools он помечен «canceled»).

В проекте это разделено на переиспользуемые части:
```ts
export function searchText(delay = 400): OperatorFunction<string, string> {
  return source => source.pipe(map(text => text.trim()), debounceTime(delay), distinctUntilChanged());
}
```
```ts
this.searchControl.valueChanges
  .pipe(searchText(), takeUntilDestroyed(destroyRef))
  .subscribe(search => this.navigate({ search: search || null, page: null }));
```
Поиск, фильтры (`FilterPanel` → `(apply)`), сортировка (клик по заголовку), размер и номер страницы
меняют **query-параметры URL**. Единый поток собирает их в запрос:
```ts
private readonly query$ = this.route.queryParamMap.pipe(map(paramsToQuery), distinctUntilChanged(sameQuery));
protected readonly state = toSignal(
  combineLatest([this.query$, this.reload$]).pipe(
    map(([query]) => query),
    loadWith(query => this.api.list(query)),   // внутри switchMap — отмена устаревших
    tap(state => this.fixPage(state)),
  ), ...);
```
Плюсы: любое изменение параметров автоматически даёт ровно один актуальный запрос; при смене фильтра
страница сбрасывается на первую; работают «назад/вперёд» и ссылки на отфильтрованный список.

Защита от повторных кликов: `exhaustMap` в `Action` (повторная отправка формы игнорируется),
`throttleTime` — для частых событий (скролл).

## 13. Клиентская валидация, обработка ошибок и управление состояниями загрузки

**Клиентская валидация** — быстрая обратная связь до отправки и меньше лишних запросов. Она **не заменяет**
серверную: запрос можно отправить в обход интерфейса, поэтому сервер проверяет всё повторно (422).

В проекте — **Reactive Forms**: форма описана в классе, у каждого поля валидаторы:
- встроенные: `Validators.required`, `pattern`, `minLength`, `maxLength`;
- свои (`core/validators.ts`): `positiveInteger`, `moveinDate(original)` (от сегодня до +6 месяцев, только если
  дата изменена), `passwordBytes` (≤ 72 байт — ограничение BCrypt), `sameAs('password')` (совпадение
  паролей), `numberList` (числа через запятую в фильтрах).
- ошибки показываются под полем, когда поле `touched` или `dirty`; при отправке невалидной формы —
  `markAllAsTouched()`; невалидное поле подсвечивается классом `ng-invalid ng-touched`.

**Обработка ошибок backend** — `toAppError()` превращает `HttpErrorResponse` в `{status, message, details}`:

| Код | Ситуация | Что видит пользователь |
|---|---|---|
| 0, 502, 503, 504 | сервер недоступен | «Сервер недоступен…», кнопка «Повторить» |
| 400 | неверные параметры | текст ошибки + «Сбросить параметры» |
| 401 | нет/истёк токен | interceptor обновляет токен; если не вышло — «Сессия истекла», переход на `/login?returnUrl=…` |
| 403 | нет прав | «Недостаточно прав для этой операции» |
| 404 | нет студента | «Студент не найден» |
| 409 | дубликат | «Студент с ИСУ … уже существует», «Имя пользователя уже занято» |
| 422 | не прошла проверка | общий текст + сообщения у конкретных полей (`details`) |
| 500 | ошибка сервера | «Внутренняя ошибка сервера, попробуйте позже» (детали не показываются) |

Ошибки в потоке перехватываются `catchError` и превращаются в данные, чтобы поток не завершался и
следующие запросы работали.

**Состояния загрузки** — каждое асинхронное действие имеет состояния: *idle → loading → success | error*.
`LoadState<T> = { loading, data, error }`. Интерфейс: индикатор `app-loader`, таблица полупрозрачна и
некликабельна во время загрузки, но старые данные остаются (нет «мигания»).

**Защита от повторной отправки**: класс `Action` — `exhaustMap` + сигнал `busy`, кнопка
`[disabled]="action.busy()"` с текстом «Сохранение...», `<fieldset [disabled]>` в форме.

## 14. Аутентификация и авторизация. JWT, access- и refresh-токены

- **Аутентификация** — проверка, *кто* пользователь (логин + пароль → токен).
- **Авторизация** — проверка, *что ему можно* (роль ADMIN/USER → доступ к операциям).

**JWT (JSON Web Token)** — строка `header.payload.signature`, каждая часть в Base64URL:
- header: `{"alg":"HS256","typ":"JWT"}`;
- payload (claims): `sub` (имя), `uid`, `role`, `type`, `iat`, `exp`;
- signature: `HMAC-SHA256(header + "." + payload, JWT_SECRET)`.

Токен **подписан, но не зашифрован**: payload может прочитать любой (так фронтенд узнаёт роль, если
сервер недоступен), но изменить его без секрета нельзя — подпись не сойдётся. Поэтому в JWT не кладут
секретные данные. Сервер **не хранит сессию** (stateless): проверяет подпись и `exp`.

**Зачем два токена.** JWT нельзя «отозвать» до истечения срока, поэтому:
- **access-токен** — короткоживущий (15 мин), отправляется с каждым запросом
  `Authorization: Bearer <token>`. Если украдут — вред ограничен по времени;
- **refresh-токен** — долгоживущий (7 дней), используется **только** для `POST /api/auth/refresh`, чтобы
  получить новую пару без ввода пароля. На сервере его `jti` хранится в БД, он **одноразовый** (ротация):
  при обновлении старый удаляется, при выходе — отзывается. Повторное использование → 401.

Поток в проекте:
1. `/login` → `POST /api/auth/login` → `{accessToken, refreshToken}` → `AuthStore.setTokens` (+ localStorage) →
   `GET /api/auth/me` → `AuthStore.setUser`.
2. `authInterceptor` добавляет заголовок `Authorization` ко всем запросам API.
3. Ответ 401 → `auth.refresh()` → новые токены → исходный запрос повторяется (`switchMap`).
   Параллельные запросы ждут одного обновления (`shareReplay`).
4. Refresh тоже 401 (истёк/отозван) → `expireSession()`: очистка стора, сообщение «Сессия истекла»,
   переход на `/login?returnUrl=…`, после входа — возврат на прежнюю страницу.
5. Выход → `POST /api/auth/logout` с refresh-токеном (сервер его отзывает) + очистка стора.
6. При перезагрузке страницы `provideAppInitializer` восстанавливает пользователя через `/me`.

Где хранить токены: `localStorage` (просто, переживает перезагрузку, но доступен JS → уязвим к XSS),
память (безопасно, но теряется при перезагрузке), `HttpOnly`-cookie (JS не может прочитать — защита от XSS,
но нужна защита от CSRF). В работе используется localStorage (как в лаб. 3) + защита от XSS (вопрос 16).

## 15. Защита маршрутов и разграничение доступа на основе ролей

**RBAC (Role-Based Access Control)** — права выдаются ролям, а роли — пользователям.
Здесь: `USER` — только чтение студентов; `ADMIN` — всё, плюс управление учетными записями.

Защита на **трёх уровнях**:

1. **Маршруты — guards** (`core/guards.ts`). Функция `CanActivateFn` вызывается до перехода и
   возвращает `true` (пустить) или `UrlTree` (перенаправить):
   ```ts
   export const adminGuard: CanActivateFn = (route, state) => {
     const store = inject(AuthStore);
     if (!store.isLoggedIn()) return router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
     if (!store.isAdmin()) { notices.error('Недостаточно прав...'); return router.createUrlTree(['/students']); }
     return true;
   };
   ```
   - `authGuard` — `/profile`, `/students`, `/students/:id` (только вошедшие);
   - `adminGuard` — `/students/new`, `/students/:id/edit`, `/users`;
   - `guestGuard` — `/login`, `/register` (вошедшего отправляет в профиль).
   Ещё бывают `canMatch` (не загружать lazy-модуль), `canDeactivate` (не уходить с несохранённой формы),
   `resolve` (загрузить данные до перехода).

2. **Интерфейс** — условный рендеринг: `@if (store.isAdmin())` для кнопок «Добавить», «Редактировать»,
   «Удалить», ссылки «Пользователи». Пользователь не видит действий, которые ему недоступны.

3. **Сервер** — главный уровень. Клиентские проверки — только удобство: JS можно изменить в DevTools,
   запрос можно отправить через curl. Бэкенд (`AuthFilter`) проверяет подпись токена и роль по
   `@RolesAllowed` и отвечает 401/403. Фронтенд обрабатывает эти ответы: 403 → сообщение,
   401 → обновление токена или выход.

Роль берётся из ответа `/api/auth/me` (а при недоступном сервере — из payload access-токена).
Если администратор понизил собственную роль, приложение выходит и просит войти заново.

## 16. Безопасность frontend-приложений. XSS, CSRF и основные способы защиты

### XSS (Cross-Site Scripting)
Внедрение чужого JS-кода на страницу. Скрипт выполняется с правами сайта: может прочитать токены из
localStorage, выполнять запросы от имени пользователя, подменить интерфейс.
- *Stored* — вредоносный код сохранён в БД (например, в «Заметках» студента `<img src=x onerror=...>`)
  и показывается всем;
- *Reflected* — код в параметре URL отражается в ответе;
- *DOM-based* — JS сам вставляет недоверенные данные в DOM (`innerHTML = location.hash`).

Защита:
- **экранирование вывода**. Angular по умолчанию экранирует всё в `{{ }}` и `[prop]`, а `[innerHTML]`
  санитизирует (вырезает скрипты и обработчики). Обход — только явный `bypassSecurityTrust...`.
  В проекте нет `innerHTML` с данными. (В лаб. 3 использовался `textContent` — тоже безопасно.)
- не использовать `eval`, `new Function`, `innerHTML` с данными пользователя;
- **Content Security Policy** — заголовок, ограничивающий источники скриптов. В Nginx:
  `default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'; ...` — даже если
  вставить `<script>` или `onerror=`, браузер не выполнит inline-скрипт. Для этого в сборке отключено
  `inlineCritical` (оно добавляет inline-обработчик `onload`);
- валидация входных данных на сервере; `HttpOnly`-cookie для токенов, чтобы JS не мог их прочитать.

### CSRF (Cross-Site Request Forgery)
Злой сайт заставляет браузер жертвы отправить запрос на наш сайт; браузер **автоматически**
прикрепляет cookie, и запрос выполняется от имени пользователя (`<form action="https://bank/transfer">`).
Защита:
- не полагаться на cookie для аутентификации. В проекте токен передаётся в заголовке `Authorization`,
  который JS добавляет явно, — чужой сайт не может его прочитать и добавить, поэтому CSRF не работает;
- если cookie нужны — `SameSite=Lax/Strict`, CSRF-токен (synchronizer token / double submit cookie;
  Angular `HttpClient` поддерживает `XSRF-TOKEN` → `X-XSRF-TOKEN`), проверка `Origin`/`Referer`;
- изменяющие операции — только не-GET методами;
- строгий CORS (у нас фронтенд и API на одном origin, CORS вообще не открыт).

### Прочее
- **Clickjacking** — сайт показывают в невидимом iframe; защита `X-Frame-Options: DENY`,
  `frame-ancestors 'none'`;
- `X-Content-Type-Options: nosniff`, `Referrer-Policy`;
- HTTPS (защита токенов при передаче), не хранить секреты во фронтенде (код виден всем),
  обновлять зависимости (`npm audit`), не показывать подробности ошибок 500 пользователю,
  короткоживущие access-токены и одноразовые refresh-токены.

## 17. Архитектура frontend-приложения. Разделение ответственности и организация проекта

Принцип: **разделение ответственности (separation of concerns)** — отображение, бизнес-логика,
работа с сетью и состояние находятся в разных местах. Тогда компоненты проще, логику можно
переиспользовать и тестировать отдельно.

Слои (из лекции) и как они представлены в проекте:

| Слой | Назначение | В проекте |
|---|---|---|
| Router | связывает URL и компоненты | `app.routes.ts`, guards |
| Pages | компоненты маршрутов: читают параметры, собирают экран | `pages/students`, `pages/student-edit`, ... |
| Features / UI-компоненты | таблица, форма, фильтры, карточки | `components/student-form`, `filter-panel`, `pagination`, `user-card` |
| Domain model | типы предметной области | `core/models.ts` (`Student`, `User`, `StudentQuery`) |
| API client | HTTP-запросы | `students.api.ts`, `users.api.ts`, `auth.service.ts` |
| State | глобальное состояние | `auth.store.ts`, `notice.store.ts` |
| Shared | общие утилиты | `rx.ts`, `errors.ts`, `validators.ts`, `auth.interceptor.ts` |

Поток данных однонаправленный: страница → API-сервис → стор/сигнал → шаблон; события снизу
вверх через outputs.

Подходы к организации папок: **по типу** (`components/`, `services/`, `pages/` — как здесь, удобно
для небольших проектов), **по фичам** (`students/`, `auth/`, `users/` — каждая со своими компонентами
и сервисами, лучше масштабируется), **Feature-Sliced Design** (слои `app → pages → widgets → features →
entities → shared`, импорты только сверху вниз).

Сравнение с лаб. 3: там один файл `scripts.js` на 660 строк делал всё — искал элементы, хранил
состояние в переменных, отправлял запросы, вручную строил строки таблицы и переключал классы.
Здесь каждая часть отвечает за одно, а DOM обновляет фреймворк.

## 18. Docker и контейнеризация. Dockerfile, образы и контейнеры

**Контейнеризация** — упаковка приложения со всем окружением (runtime, библиотеки, конфиги) в
изолированную единицу, которая одинаково работает на любой машине («у меня работает» → «работает
везде»). В отличие от виртуальной машины контейнер не содержит своего ядра ОС: использует ядро хоста,
а изоляция делается механизмами Linux — **namespaces** (свои процессы, сеть, файловая система)
и **cgroups** (лимиты CPU/памяти). Поэтому контейнеры лёгкие и стартуют за секунды.

- **Образ (image)** — неизменяемый шаблон: набор **слоёв** файловой системы + метаданные (команда
  запуска, переменные, порты). Каждая инструкция Dockerfile создаёт слой; слои кэшируются и
  переиспользуются между образами.
- **Контейнер** — запущенный экземпляр образа: образ + тонкий записываемый слой сверху + процесс.
  Из одного образа можно запустить много контейнеров. Данные в контейнере пропадают при его удалении,
  для постоянных данных — **volumes** (у нас `pgdata` для PostgreSQL) или bind mount (папка хоста —
  в dev-режиме `./frontend:/frontend`).
- **Registry** — хранилище образов (Docker Hub, quay.io): `docker pull nginx:stable-alpine`.

**Dockerfile** — инструкция сборки образа:
| Инструкция | Назначение |
|---|---|
| `FROM` | базовый образ (`FROM node:24-slim AS build`) |
| `WORKDIR` | рабочая папка |
| `COPY` / `ADD` | скопировать файлы (`ADD` умеет URL/архивы) |
| `RUN` | выполнить команду при сборке (`npm ci`) — новый слой |
| `ENV` / `ARG` | переменная окружения / аргумент сборки |
| `EXPOSE` | документирует порт |
| `CMD` / `ENTRYPOINT` | команда при запуске контейнера |
| `USER` | от какого пользователя запускать |

Кэширование: если файл не менялся, слой берётся из кэша. Поэтому сначала копируются только
`package.json` и `package-lock.json` и ставятся зависимости, а потом — исходники: при изменении кода
`npm ci` не повторяется. `.dockerignore` исключает `node_modules`, `dist`, `.angular` из контекста сборки.

Основные команды: `docker build -t name .`, `docker run -p 8080:80 name`, `docker ps`, `docker logs`,
`docker exec -it <c> sh`, `docker stop/rm`, `docker images`.

## 19. Многоэтапная сборка Docker. Сборка frontend и раздача статических файлов через Nginx

**Multi-stage build** — в одном Dockerfile несколько `FROM`; каждый — отдельный этап.
Финальный образ строится только из последнего этапа, а из предыдущих копируются лишь нужные
файлы (`COPY --from=build`). Инструменты сборки (Node.js, npm, исходники, `node_modules` — сотни МБ)
в итоговый образ не попадают.

`frontend/Dockerfile`:
```dockerfile
FROM node:24-slim AS build                 # этап 1: сборка
WORKDIR /app
COPY lab4/package.json lab4/package-lock.json ./
RUN npm ci --no-audit --no-fund            # точные версии из lock-файла
COPY lab4/ .
RUN npx ng build --configuration production  # → dist/lab4/browser: index.html, js, css

FROM nginx:stable-alpine                   # этап 2: раздача
COPY nginx/default.conf.template /etc/nginx/templates/default.conf.template
COPY --from=build /app/dist/lab4/browser /usr/share/nginx/html
ENV BACKEND_URL=http://backend:8080
EXPOSE 80
```
Итог: образ фронтенда ~90 МБ (nginx:alpine + статика) вместо ~1 ГБ, меньше поверхность атаки, быстрее скачивание. Бэкенд собран так же:
Maven-этап → WAR → образ WildFly.

**Production-сборка Angular**: компиляция шаблонов AOT, минификация, tree-shaking (удаление
неиспользуемого кода), хеши в именах файлов (`main-7DZZWZQF.js`) для долгого кэширования.
Результат — **статические файлы**, которым не нужен Node.js — их может раздать любой веб-сервер.

**Nginx** — быстрый веб-сервер и обратный прокси. Конфиг `frontend/nginx/default.conf.template`:
- `root /usr/share/nginx/html` — раздаёт статику;
- `location / { try_files $uri $uri/ /index.html; }` — **SPA fallback**: если файла нет (например
  `/students/5`), отдаётся `index.html`, а маршрут разбирает Angular;
- `location /api/ { proxy_pass $backend; }` — **reverse proxy**: запросы к API уходят в контейнер
  бэкенда, для браузера всё на одном адресе (нет CORS);
- статика с хешами — `expires 30d`, `index.html` — `no-cache` (чтобы новая версия подхватывалась сразу);
- заголовки безопасности (CSP и др.);
- `resolver 127.0.0.11` — DNS Docker, имя `backend` разрешается при каждом запросе, поэтому Nginx
  не падает, если бэкенд ещё не запущен, и находит его после перезапуска;
- шаблон: при старте образ nginx выполняет `envsubst` для файлов из `/etc/nginx/templates/` —
  `${BACKEND_URL}` подставляется из переменной окружения.

## 20. Docker Compose. Сети контейнеров, переменные окружения и взаимодействие frontend с backend

**Docker Compose** — описание многоконтейнерного приложения в одном YAML-файле и управление им
одной командой: `docker compose up --build` (собрать и запустить), `down` (удалить), `down -v`
(вместе с томами), `logs -f`, `ps`, `stop`/`start`.

`docker-compose.yml` проекта — три **сервиса**:
- `db` — `postgres:17`, том `pgdata`, `healthcheck` через `pg_isready`;
- `backend` — собирается из `./backend`, `depends_on: db: condition: service_healthy` (стартует,
  только когда база готова принимать соединения);
- `frontend` — собирается из `./frontend`, `depends_on: backend`, `ports: "${APP_PORT:-8080}:80"`.

**Сети.** Compose создаёт для проекта общую bridge-сеть (`lab4_default`). Внутри неё работает
встроенный DNS: контейнер доступен по **имени сервиса** — бэкенд подключается к `db:5432`,
Nginx проксирует на `backend:8080`. IP-адреса знать не нужно. Наружу (на хост) открыт только порт
фронтенда (`ports`); база и бэкенд недоступны извне — это безопаснее. Можно создавать несколько
сетей и изолировать сервисы друг от друга.

**Переменные окружения** — способ вынести настройки, зависящие от окружения, из кода (принцип
12-factor app): пароли, секреты, адреса, порты.
- Compose читает файл `.env` рядом с `docker-compose.yml` и подставляет значения: `${DB_PASSWORD:-students}`
  — значение из `.env` или окружения, иначе значение по умолчанию. Благодаря значениям по умолчанию
  проект запускается без ручной настройки.
- `environment:` передаёт переменные внутрь контейнера: WildFly читает их через MicroProfile Config
  (`JWT_SECRET`, `DB_URL`), Nginx — через шаблон (`BACKEND_URL`).
- `.env.example` — пример в репозитории; настоящий `.env` с секретами в git не коммитят.

**Взаимодействие frontend и backend:**
```
Браузер ──HTTP──► localhost:8080 ──► frontend (nginx:80)
   GET /students        → index.html (SPA fallback) → Angular показывает список
   GET /main-*.js       → статический файл
   GET /api/requests?.. → proxy_pass http://backend:8080/api/requests?..
                                         └─► WildFly ──JDBC──► db:5432
```
Angular обращается к API по относительному пути `/api/...`, поэтому адрес бэкенда в коде фронтенда
нигде не зашит: в разработке (`docker-compose_dev.yml`) тот же путь проксирует отдельный Nginx на
`ng serve`, в продакшене — Nginx внутри образа фронтенда. Браузер видит один origin, поэтому не нужны
CORS-заголовки, а токен из заголовка `Authorization` спокойно проходит через прокси.
