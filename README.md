# Лабораторная работа №4

Фронтенд системы учёта студентов, перенесённый с чистых HTML + CSS + JS (лаб. 3, папка `lab3_2`)
на Angular 22 + RxJS. Бэкенд — REST API из лаб. 3 (Jakarta EE, WildFly, PostgreSQL, JWT), в него добавлен
только эндпоинт для изменения своего профиля. Всё приложение собирается и запускается в Docker Compose, фронтенд раздаёт Nginx.

## Запуск

Нужен только Docker (с плагином Compose). Из корня проекта:

```
docker compose up --build
```

Все параметры берутся из переменных окружения, значения по умолчанию в коде и в `docker-compose.yml`
не заданы. Compose читает их из файла `.env` в корне проекта — он уже заполнен, поэтому ручная настройка
не нужна. Если `.env` нет, создайте его из примера (`cp .env.example .env`) и задайте `JWT_SECRET`
(например `openssl rand -hex 32`), иначе Compose остановится с сообщением, какой переменной не хватает.
Бэкенд стартует около 20–40 секунд (строка `WFLYSRV0025 ... started` в логе), до этого фронтенд
открывается, но на запросы к API показывает «Сервер недоступен».

- Приложение: http://localhost:8080/
- Swagger UI: http://localhost:8080/swagger.html
- Администратор: `admin` / `change-me-please`

Запуск в фоне: `docker compose up --build -d`, логи: `docker compose logs -f backend`.

Остановка:

```
docker compose stop          # остановить контейнеры
docker compose down          # удалить контейнеры (база сохраняется в томе pgdata)
docker compose down -v       # удалить контейнеры вместе с базой
```

## Настройки

Все параметры, зависящие от окружения, вынесены из кода в переменные окружения. В `docker-compose.yml`
они подставляются как `${JWT_SECRET:?...}`: значения по умолчанию нет, переменная обязательна.
Значения задаются в `.env` в корне проекта (пример со всеми ключами — `.env.example`):

| Переменная               | Назначение                                                   |
|--------------------------|--------------------------------------------------------------|
| `APP_PORT`               | порт на хосте, на котором открывается сайт                   |
| `BACKEND_URL`            | адрес бэкенда для Nginx внутри сети Compose (`http://backend:8080`) |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | база PostgreSQL                                   |
| `JWT_SECRET`             | ключ подписи JWT, не короче 32 символов                      |
| `JWT_ACCESS_TTL_MINUTES` | время жизни access-токена                                    |
| `JWT_REFRESH_TTL_DAYS`   | время жизни refresh-токена                                   |
| `ADMIN_USERNAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` | администратор, создаётся при первом старте, если его ещё нет |

Как переменные доходят до приложения: Compose передаёт их в контейнеры через `environment:`.
WildFly читает их через MicroProfile Config (`@ConfigProperty`), PostgreSQL — через `POSTGRES_*`,
Nginx подставляет `BACKEND_URL` в конфиг при старте контейнера
(`frontend/nginx/default.conf.template`, механизм `envsubst` образа nginx).
`.env` содержит секреты, поэтому его не стоит хранить в git — в репозитории должен быть только `.env.example`.
Для быстрой проверки обновления токенов можно поставить `JWT_ACCESS_TTL_MINUTES=1`.

Если база уже была создана с другим паролем, после смены `DB_USER`/`DB_PASSWORD` нужен `docker compose down -v`.

## Как устроен запуск

```
браузер ──► frontend (nginx:80, наружу APP_PORT)
              ├─ /            статические файлы Angular, для любых путей SPA отдаётся index.html
              ├─ /api/...     proxy_pass ──► backend (WildFly:8080) ──► db (PostgreSQL:5432)
              └─ /swagger.html, /openapi ──► backend
```

- `frontend/Dockerfile` — многоэтапная сборка: этап `node:24-slim` ставит зависимости (`npm ci`)
  и собирает Angular (`ng build`), второй этап `nginx:stable-alpine` получает только папку `dist/lab4/browser`
  и шаблон конфига. Node.js и исходники в итоговый образ не попадают.
- `backend/Dockerfile` — тоже многоэтапная: Maven собирает `students.war`, WildFly его запускает.
- Все сервисы в одной сети Compose и обращаются друг к другу по имени сервиса (`backend`, `db`).
  Наружу открыт только порт Nginx, поэтому фронтенд и API на одном origin — CORS не нужен.
- Nginx отдаёт заголовки безопасности (CSP, `X-Frame-Options`, `X-Content-Type-Options`),
  кэширует статику с хешами в именах и не кэширует `index.html`.

## Режим разработки

`docker-compose_dev.yml` поднимает dev-сервер Angular (`ng serve`) с горячей перезагрузкой
внутри контейнера, бэкенд, базу и отдельный Nginx на 80 порту:

```
docker compose -f docker-compose_dev.yml up --build
```

Сайт: http://localhost/. Контейнер фронтенда работает от пользователя `1000:1000`, поэтому
созданные им файлы (`node_modules`, `.angular`) принадлежат пользователю хоста, а не root.

Без Docker фронтенд собирается так (нужен Node.js 22+):

```
cd frontend/lab4
npm ci
npx ng build        # результат в dist/lab4/browser
```

## Маршруты

| Путь                  | Доступ        | Что делает                                            |
|-----------------------|---------------|-------------------------------------------------------|
| `/`                   | все           | главная                                               |
| `/login`              | гости         | вход                                                  |
| `/register`           | гости         | регистрация (после неё вход выполняется автоматически)|
| `/profile`            | вошедшие      | профиль, права, изменение своих данных, выход         |
| `/students`           | вошедшие      | список: поиск, фильтры, сортировка, пагинация         |
| `/students/:id`       | вошедшие      | досье студента, выгрузка в JSON, удаление (ADMIN)     |
| `/students/new`       | ADMIN         | добавление                                            |
| `/students/:id/edit`  | ADMIN         | редактирование: студент сохраняется целиком таким, как в форме (PUT) |
| `/users`              | ADMIN         | учетные записи: поиск, фильтры, сортировка, пагинация, удаление |
| `/users/new`          | ADMIN         | создание учетной записи с любой ролью                 |
| `/users/:username`    | ADMIN         | карточка учетной записи, удаление                     |
| `/users/:username/edit` | ADMIN       | редактирование: имя, почта, роль, новый пароль        |
| `**`                  | все           | страница 404                                          |

Гость, открывший защищённую страницу, попадает на `/login?returnUrl=...` и после входа возвращается обратно.
Пользователь с ролью USER не видит кнопок изменения, а на страницы администратора его не пускает `adminGuard`.
Даже если обойти проверки на клиенте, бэкенд ответит 403 — интерфейс покажет сообщение об этом.

## Как выполнены требования

**Компоненты.** Страницы (`pages/`) собирают экран из компонентов (`components/`). Разделы «Студенты»
и «Пользователи» построены из одних и тех же компонентов и отличаются только описанием полей
(`STUDENT_FIELDS`/`STUDENT_FILTERS` и `USER_FIELDS`/`USER_FILTERS` в `models.ts`):
- `ListToolbar` — поиск, кнопка фильтров, размер страницы, свои кнопки через `<ng-content>`;
- `FilterPanel` — форма фильтров строится по списку полей (`list`, `numbers`, `single`, `date`, `checkboxes`);
- `DataTable` — таблица с сортировкой по клику на заголовок, действия строки передаются шаблоном
  (`<ng-template #actions let-row>` → `ngTemplateOutlet`);
- `Pagination`, `Loader`, `ConfirmButton` (удаление в два нажатия);
- `DetailCard` — карточка просмотра (досье студента, учетная запись, профиль);
- `StudentForm`, `UserForm` — формы; `UserForm` используется для создания и редактирования учетной записи
  и для своего профиля (`[showRole]="false"`).
Логика списка (URL → запрос → загрузка → автообновление) вынесена в класс `ListState` (`core/list-state.ts`),
его создают обе страницы списков; загрузка карточки с опросом — оператор `loadAndPoll` (`core/rx.ts`).
Данные идут через `input()`, события — через `output()` (`(apply)`, `(pageChange)`, `(sortChange)`,
`(confirmed)`, `(submitted)`). Локальное состояние — сигналы внутри компонентов (`showFilters`, `showExtra`,
`armed` в `ConfirmButton`, `editing` в профиле). Жизненный цикл — `ngOnChanges` в `StudentForm`, `UserForm`,
`FilterPanel`, `ListToolbar` (заполнение формы при смене входных данных), `DestroyRef` / `takeUntilDestroyed`.
Условный рендеринг — `@if / @else / @for ... @empty`. Маршрутизация — Angular Router, параметр `:id`
приходит в компонент как input (`withComponentInputBinding`).

**Глобальное состояние.** `AuthStore` на Angular Signals: `user`, `accessToken`, `refreshToken`
и вычисляемые `isLoggedIn`, `isAdmin`. Им пользуются navbar, guards, interceptor и страницы.
`NoticeStore` — общая очередь уведомлений.

**RxJS** (`core/rx.ts` + места использования):
- `searchText()` — оператор для строки поиска: `map(trim)`, `debounceTime(400)`, `distinctUntilChanged()`.
- `loadWith()` — оператор загрузки: `switchMap` отменяет устаревший HTTP-запрос, `startWith` даёт
  состояние загрузки, `catchError` превращает ошибку в данные, `scan` сохраняет прошлые данные на время загрузки.
- `Action` — класс для отправки форм: `Subject` + `exhaustMap` (повторные нажатия игнорируются, пока
  запрос идёт), сигнал `busy` для блокировки кнопки, `share()` для общего результата.
- Список студентов: состояние запроса хранится в URL; `queryParamMap` → `map` → `distinctUntilChanged`
  → `combineLatest` с потоком перезагрузки → `loadWith` → `toSignal`. Поиск, фильтры, сортировка и
  страницы просто меняют URL, поэтому работают кнопки «назад/вперёд» и ссылка на отфильтрованный список.
- Interceptor: `catchError` на 401 → `refresh()` (одна общая операция обновления через `shareReplay`,
  даже если упало несколько запросов сразу) → `switchMap` повторяет исходный запрос с новым токеном.
- Регистрация: `register` → `switchMap` → `login` → `switchMap` → `/me`.
- Автообновление: `poll()` раз в 15 секунд (`POLL_PERIOD` в `rx.ts`) даёт сигнал на фоновое обновление.
  Пока вкладка скрыта, опрос остановлен (`fromEvent(document, 'visibilitychange')` + `switchMap` → `EMPTY`),
  при возвращении на вкладку данные обновляются сразу. Так обновляются текущий пользователь (`App`, запрос
  `/api/auth/me`), список учетных записей у администратора, список студентов и досье студента
  (если студента удалили, вместо досье появится «Студент не найден»). Форма редактирования
  не обновляется. Фоновое обновление «тихое»:
  нет индикатора загрузки, а при ошибке сети остаются прежние данные. Фильтры, сортировка, страница и
  открытая панель фильтров сохраняются (запрос берётся из URL через `withLatestFrom`), позиция прокрутки не
  сбрасывается (строки отслеживаются по `track student.id`), начатое редактирование учетной записи не
  закрывается, если её данные не изменились.

**Ошибки и загрузка.** `errors.ts` переводит ответ в понятный текст: 0 / 502 / 503 / 504 —
сервер недоступен, 401 — нужна авторизация (или сессия истекла — тогда выход и переход на `/login`),
403 — недостаточно прав, 404 — студент не найден, 409 — уже существует, 422 — текст ошибки
и подсказки у конкретных полей формы, 500 — внутренняя ошибка. Индикатор загрузки (`app-loader`),
полупрозрачная таблица во время обновления, кнопки «Сохранение...» и блокировка форм.
Если при открытии сайта бэкенд недоступен, сессия не сбрасывается: пользователь берётся из access-токена,
а на страницах видна ошибка с кнопкой «Повторить».

**Валидация.** Reactive Forms с теми же правилами, что на сервере: ИСУ — положительное целое,
ФИО — минимум два слова, группа `P3223`, общежитие и комната — положительные, дата заселения — от сегодня
до +6 месяцев (при редактировании только если дата изменена), заметка до 500 символов; имя пользователя
`[A-Za-z0-9_]{3,32}`, почта, пароль 8+ символов и не больше 72 байт, совпадение паролей.
В фильтрах числовые поля проверяются до отправки, чтобы не получать 400 от сервера.

## Размеры

Размеры заданы в `rem`, `vw` и `vh`, а не в пикселях. Базовый шрифт `html` растёт с шириной окна:
`clamp(1rem, 0.7rem + 0.6vw, 1.9rem)` — примерно 16px на телефоне, 19px на 1280px, 23px на 1920px
и 27px на 2560px, вместе с ним масштабируются иконки, кнопки, отступы и поля. Ширина и внешние отступы
страницы — в `vw`/`vh`. В пикселях оставлены только рамки толщиной 1px и звёздный фон из шаблона
(`components/stars`): там координаты звёзд задаются по полю 2560×2000px.

## Что поменялось в заготовке

- Шаблон Angular дописан; страница `regeister` переименована в `register`, шаблонные `*.spec.ts` удалены.
- Бюджет размера стилей компонента увеличен: компонент `stars` генерирует ~70 КБ теней.
- Из `backend/src/main/webapp` убран старый фронтенд (index.html, static/) — теперь его заменяет Angular.
- `docker-compose_dev.yml` теперь сам запускает `ng serve`; `nginx/nginx.conf` проксирует WebSocket для HMR.
- Добавлены `docker-compose.yml`, `.env.example`, `frontend/Dockerfile`, `frontend/nginx/`.
- В бэкенд добавлен `PATCH /api/auth/me` (любая роль): изменить своё имя, почту или пароль.
  Аутентификация — по access-токену, изменяется только своя учетная запись (имя берётся из токена).
  Тело: `{"username", "email", "password"}`, все поля необязательные. Роль так поменять нельзя. Ответ — новая пара токенов, потому что
  при смене имени или пароля старые токены отзываются. Код: `ProfileUpdateRequest`,
  `AuthService.updateProfile`, `AuthResource.updateMe`.

- В бэкенд добавлен `POST /api/users` (только ADMIN): создать учетную запись.
  Тело: `{"username", "email", "password", "role"}`, правила проверки те же, что при регистрации.
  Ответ — 201 и созданный пользователь; занятые имя или почта — 409 с подсказками у полей.
  Код: `UserCreateRequest`, `UserService.create`, `UserResource.create`.
- `GET /api/users` теперь работает как список студентов: фильтры `username`, `email`, `role` (точное
  совпадение, повтор параметра — ИЛИ), `search` (подстрока в имени или почте), `sort` (`id`, `username`,
  `email`, `role`, `-` — по убыванию), `page`, `size`. Ответ — страница
  `{"items", "page", "size", "totalItems", "totalPages"}` вместо массива. Код: `UserQueryParser`,
  `UserQuery`, `UserPage`, `UserRepository.find/count`.
- Добавлен `DELETE /api/users/{id}` (только ADMIN): 204; последнего администратора удалить нельзя — 422;
  нет такой — 404. Удалить можно и свою учетную запись.
- Добавлен `DELETE /api/auth/me` (любая роль): удалить свою учетную запись, 204. В профиле это кнопка
  «Удалить аккаунт». После удаления своей учетной записи (из профиля или из раздела «Пользователи»)
  фронтенд сразу выходит из системы и открывает страницу входа.
  Refresh-токены удаляемого пользователя удаляются вместе с ним (каскад в БД).
- Фронтенд адресует учетные записи по имени (`/users/:username`), ID на экран не выводится.
- В коллекцию Postman (`backend/postman`) добавлены запросы на новые эндпоинты; в конце коллекция удаляет
  созданных ею пользователей. Прогон: `postman collection run backend/postman/students.postman_collection.json`.

## Профиль и навигация

- В профиле не показываются служебные данные (ID учетной записи, срок действия токена) — только имя,
  почта, роль и права. Кнопка «Редактировать профиль» открывает форму: имя, почта, новый пароль
  (ни текущий пароль, ни повтор нового не спрашиваются). После сохранения пользователь остаётся в системе с новыми токенами.
- На узких экранах (до 700px) все надписи в навбаре заменяются иконками (компонент `components/icon`,
  встроенные SVG), подписи остаются во всплывающих подсказках `title`.
